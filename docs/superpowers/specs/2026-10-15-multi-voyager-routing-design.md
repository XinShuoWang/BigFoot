# 多 Voyager 与 Gate 集中分流设计（已确认）

## 目标与范围

保留上海 Gate，支持香港、新加坡、东京三个 Voyager。客户端继续连接同一个 Gate，使用原有 Trojan over WSS 协议。所有出口选择由 Gate 完成，对用户透明。

用户的重点是方便维护大量域名名单；默认 Voyager 也必须可配置。首版采用本地文本规则集，不执行 PAC JavaScript，不引入在线订阅、自动故障切换或 HTTPS 内容解析。

## 配置入口与兼容

`.bigfoot/config.json` 仍是主配置入口，增加命名 Voyager 列表与路由配置；规则文件是该配置显式引用的用户维护输入，`generated/` 始终是派生产物。

新配置使用 version 3，将单个 `deployment.voyager` 扩展为 `deployment.voyagers`，以 `hongkong`、`singapore`、`tokyo` 为节点 ID。每个节点有独立地区、函数名称、域名和凭证引用；Gate 保留在 `deployment.gate`。角色值仍为 `gate` / `voyager`，节点 ID 不替代角色名称。

现有 version 2 配置继续可读，内部等价为单个 `hongkong` 节点、空规则和香港默认出口。显式迁移命令将其转换为 version 3，保留现有香港函数名称、域名、客户端密码、口令和身份；迁移先创建私有备份，再原子写入配置。新节点仅在显式添加时生成独立凭证。损坏或不支持的配置不得被覆盖。

路由片段示例（不含实际部署信息或凭证）：

```json
{
  "routing": {
    "default": "hongkong",
    "rules": [
      {"rule_set": "rules/tokyo.txt", "voyager": "tokyo"},
      {"rule_set": "rules/singapore.txt", "voyager": "singapore"}
    ]
  }
}
```

规则路径相对主配置文件所在目录解析，必须是该目录内的本地文件；拒绝路径逃逸及符号链接。允许多个规则集指向同一 Voyager。规则列表允许为空，默认节点必须存在，任何未知节点引用均使配置校验失败。

## 规则文件与匹配语义

UTF-8 文本，每行一条，允许空行和以 `#` 开头的整行注释：

```text
# 精确匹配
DOMAIN,api.example.com
# 匹配域名本身及所有子域名
DOMAIN-SUFFIX,example.jp
# 仅匹配客户端直接提交的目标 IP
IP-CIDR,203.0.113.0/24
IP-CIDR6,2001:db8::/32
# 目标端口
DST-PORT,443
```

示例地址仅作格式说明；Voyager 的公网地址安全策略仍独立执行。

每行是独立的匹配条件，同一文件内各行是“或”关系。按 `routing.rules` 顺序逐个匹配规则集，第一组命中决定出口；无命中时使用 `routing.default`。域名比较忽略大小写，移除一个结尾根点，国际域名统一为 IDNA ASCII；域名后缀按标签边界匹配，`example.jp` 不会匹配 `badexample.jp`。

IP 规则仅作用于原始目标为 IP 的连接，不为域名规则额外做 Gate 侧 DNS 查询。客户端只提交 IP 时，无法应用域名规则。首版不做 SNI 嗅探、进程识别、URL 路径匹配或域名关键词匹配。

重复规则允许并去重，跨规则集重叠按顺序处理。语法错误必须报告文件、行号和错误类型；拒绝未知指令，不能静默忽略。规则文件内不允许指定出口、DIRECT 或 REJECT，出口统一由主配置控制。

## Gate 与身份边界

认证客户端后，根据目标 host:port 选择 Voyager，再使用该节点独立的 WSS 地址、口令和 TLS 信任证书建立隧道。每条 TCP 连接只在建立时选一次出口。节点连接失败返回连接错误，不自动改用其他地区。

每个 Voyager 仅接收自身身份私钥和自身口令；Gate 持有各节点信任证书及连接口令，不接收身份私钥。配置校验比较解码后的 PEM 内容，Gate 还比较证书公钥，拒绝共享节点身份。保留内层 TLS 1.3、证书有效期和 `voyager.internal` 主机名校验，各 Voyager 继续执行目标公网检查和 DNS 固定。

路由表在启动时完成校验并编译为内存索引，连接处理中不读取规则文件。精确域名使用哈希表，后缀使用域名标签索引，IP 网段使用前缀索引，端口使用集合；跨规则集优先级保持配置顺序。每个输入文件不超过 8 MiB，合计不超过 32 MiB、200,000 条有效规则，超限显式拒绝。规范化路由 JSON 也受 32 MiB 限制。该上限是输入限制，不代表已验证的吞吐或内存容量。

运行时通过独立的结构化路由配置文件加载节点与规则；单 Voyager 的已有命令行参数继续兼容，多节点配置与旧上游参数冲突时报错。部署工具打包规范化规则和不含凭证的节点元数据，凭证继续通过受控运行时环境提供。不得将私有环境配置写进代码 ZIP、部署状态或日志。

## 部署与更新

部署前检查所有配置和规则，再编译并校验服务配置。全量部署按节点列表部署所有 Voyager，逐一保存地址并检查健康，然后部署 Gate。部署工具为每个节点选择对应区域的云端客户端，不能假定当前云账号已具备新加坡或东京权限。

保留 `--only gate` 与 `--only voyager`；后者部署全部 Voyager，增加 `--voyager NODE_ID` 用于选择单个 Voyager，选择参数仅允许与 `--only voyager` 联用。部署记录按角色和节点区分。中途失败保留已取得地址，重跑仍向云端查询实际状态。

修改名单或默认出口后，执行 `./bigfoot deploy --only gate` 生效；不要求客户端重新导入配置。首版随 Gate 更新加载规则，不实现热加载；Gate 更新仍可能中断已有会话。

客户端导出保持单一 Gate 节点。文档同步说明迁移、新地区权限、规则优先级、规则更新和故障行为。

## 验证与验收

本地 Go 测试覆盖匹配边界、顺序、默认出口、错误节点、认证前不拨号、不同节点证书/口令隔离，以及单配置兼容。多 Voyager 集成测试使用可辨识的测试端点确认每条规则实际选择的节点，不能只验证配置加载成功。

Python 测试覆盖 version 2 兼容、显式迁移与失败恢复、规则校验与打包、逐节点部署、仅更新 Gate、单节点部署、客户端导出及凭证不进入 ZIP。按 CONTRIBUTING 执行 Go race、vet、Python 单元测试及构建；依赖可用时运行 Mihomo 本地 smoke。

云端健康检查逐个覆盖 Gate 和全部 Voyager。完整 Mihomo 验收需使用临时验收规则，通过同一 Gate 强制选中每个节点，对公网 HTTPS 目标实际发起请求，结合不含目标和凭证的节点选择标记验证路径，再验证错误客户端密码被拒绝。部署中的完整验收临时逐次发布仅含一个被测节点的 Gate 路由配置，通过同一个上海 Gate 实测 HTTPS 和错误密码拒绝；唯一上游及其独立证书/口令提供路径证据。最后恢复正式策略并再次验收，普通异常或中断也尝试恢复；强制终止或断电后须重新部署 Gate。只读 verify 仅代表当前路径，不能凭一次公网响应成功推断全部出口已被使用。

云端权限、地区可用性、手机 GUI、长连接、容量、冷启动和费用均不预先声称通过。没有 Mihomo 或云权限时，明确记录验证缺口。
